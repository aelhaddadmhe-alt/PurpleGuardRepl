Fix 1 — EDR / XDR LDS billing: 1 LDS per 100 endpoints (step-wise)
Where: The DEVICES array and devLDS() function.

Step A — Add per100: true flag to the EDR entry in DEVICES
Find the EDR entry (it currently looks like this):

js

Change it to:

js

Step B — Update devLDS() to handle per100 devices
Find the devLDS function. It currently returns:

js
return d.per50 ? Math.ceil(cnt/50) : cnt;
Replace that single return line with:

js
if (d.per50)  return Math.ceil(cnt/50);
if (d.per100) return Math.ceil(cnt/100);
return cnt;
Logic: Each group of 100 EDR endpoints = 1 LDS. 101 endpoints = 2 LDS. 200 = 2 LDS. 201 = 3 LDS. This is the same step-wise ceiling pattern already used for workstations (per 50).

Fix 2 — EDR EPS estimation: use LDS-unit count, not raw endpoint count
Where: The devEPS() function.

Why: The epsTyp: 30 value for EDR means 30 EPS per 100-endpoint block (i.e., per LDS unit), NOT 30 EPS per individual endpoint. This was confirmed against the reference EPS estimation spreadsheet. Using raw count gives a 100× overestimate for EDR-heavy environments.

Find the devEPS function. It currently ends with:

js
var cnt = parseInt(document.getElementById('c-'+siteIdx+'-'+d.id).value)||0;
return cnt * d.epsTyp;
Change it to:

js
var cnt = parseInt(document.getElementById('c-'+siteIdx+'-'+d.id).value)||0;
if (d.per100) return Math.ceil(cnt/100) * d.epsTyp; // epsTyp = EPS per 100-endpoint block
return cnt * d.epsTyp;
Do NOT add a similar guard for d.per50 (workstations). Workstations' epsTyp: 3 = 3 EPS per individual workstation — raw count × 3 is already correct for them.

Verification
With 300 EDR endpoints:

Before fix: 300 × 30 = 9,000 EPS ❌
After fix: Math.ceil(300/100) × 30 = 90 EPS ✅
Fix 3 — Remove the LDS fallback from EPS estimation (storage must be purely EPS-driven)
Where: Two places in the file — showResults() and openQuote() (the email generation function).

Why: The old fallback grand * 40 used total LDS count to estimate EPS when no device data was entered. After the EDR per-100 change, this fallback produces results that are 100× smaller than before for EDR-heavy scenarios. Storage must be driven exclusively by device EPS data or the user's manual EPS override — never by LDS.

In showResults() — find:
js
var eps = epsOvr>0?epsOvr:(grandEPS>0?grandEPS:grand*40);
Replace with:

js
var eps = epsOvr>0 ? epsOvr : grandEPS;
In openQuote() — find:
js
var eps = parseFloat(epsOvr)>0?parseFloat(epsOvr):(grandEPS>0?grandEPS:grand*40);
Replace with:

js
var eps = parseFloat(epsOvr)>0 ? parseFloat(epsOvr) : grandEPS;
Result: If no devices are configured, storage shows 0 GB (honest) rather than an LDS-derived estimate (incorrect).

Fix 4 — Server specification: select tier by EPS throughput, not LDS count alone
Where: The SPECS array and the server spec selection block inside showResults().

Why: SPECS tier was previously selected purely by LDS count (getTier(SPECS, grand)). After the EDR per-100 change, a customer with 300 EDR endpoints has only 3 LDS — which maps to the smallest server spec — but still generates 90 EPS worth of indexed data. The server hardware must be sized for actual throughput, which is EPS-driven. The fix selects whichever tier is larger: the one implied by LDS count or the one implied by actual EPS.
